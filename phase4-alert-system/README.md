# HealthTrack Phase 4: Real-Time Alert System

The alert system for the HealthTrack home cardiac rehabilitation monitor, built on the Phase 3 FastAPI backend
(copied forward into this folder; `phase3-backend/` stays as submitted). Every reading a home device sends is
checked against the patient's own limits, trend rules watch activity patterns, alerts are prioritized and
deduplicated so clinicians are not flooded, notifications go out on the dashboard, email, and SMS, unanswered alerts
escalate, and every state change is kept as searchable history. New readings and alerts are pushed to connected
dashboards over a WebSocket (the dashboard itself is `../phase4-dashboard/`). All data is synthetic.

## What is in this phase

| Requirement | Where |
|---|---|
| Threshold monitoring with patient-specific limits | `app/alerts/engine.py` (`evaluate_readings`, `ThresholdResolver`); limits from a patient override, else the exercise prescription, else the program default |
| Activity pattern detection | `app/alerts/patterns.py`: missed sessions, minutes in target zone, resting heart rate trend, step decline, data gaps |
| Notification system and payloads | `app/alerts/notifications.py`: dashboard (WebSocket), email (SMTP), SMS (gateway webhook); outbox pattern with retries and a morning digest |
| Prioritization and alert-fatigue controls | `AlertEngine.raise_alert`: four severities, duplicate folding, suppression windows, masking by a more severe alert, an hourly storm cap; critical alerts are never suppressed |
| Alert logging and history | `alerts` and append-only `alert_events` tables (migration `0003_alerting`) |
| Acknowledgment by authorized users | `POST /api/v1/alerts/{id}/acknowledge` and `/resolve` (care-team clinicians and physicians only) |
| Escalation rules | `AlertEngine.run_escalations` and `escalation_policies` (critical: supervising physician at 15 min, whole care team at 30) |
| History search | `GET /api/v1/alerts` (patient, severity, status, rule, date range, acknowledging user), `GET /api/v1/alerts/{id}` (timeline), `GET /api/v1/alerts/metrics` |
| Real-time push | `app/realtime/` and `GET ws://.../api/v1/stream` |

## Setup (macOS, Linux, or Windows)

Requires Python 3.10 to 3.14. With [uv](https://docs.astral.sh/uv/):

```bash
cd phase4-alert-system
uv venv && source .venv/bin/activate          # Windows: .venv\Scripts\activate
uv pip install -r requirements-dev.txt

python3 -m alembic upgrade head               # migrations 0001 to 0003 (0003 adds alerting and default rules)
python3 -m scripts.seed                       # sample patients, prescriptions, and a realistic alert history
python3 -m uvicorn app.main:app               # api on http://localhost:8000, background alert jobs start with it
```

Open **http://localhost:8000/docs** and log in as `marcus.lee@healthtrack.example` / `HealthTrack-Demo-2026!`.

To see alerts happen live, start the device simulator in a second terminal (same folder, venv active):

```bash
python3 -m scripts.simulate_devices          # thomas crosses his heart rate ceiling about 30 s in
```

Email and SMS are written to `outbox/email.jsonl` and `outbox/sms.jsonl` unless `HT_SMTP_HOST` or
`HT_SMS_WEBHOOK_URL` is set (see `.env.example`).

## Tests and reports

```bash
python3 -m pytest                           # 305 tests, about 15 seconds
./scripts/run_reports.sh                    # tests, coverage, scenario report, both benchmarks, openapi export
```

`run_reports.sh` writes `reports/test_results.md` (testing scenarios and results), `reports/alert_performance.md`
(performance metrics), and `reports/performance.md` (Phase 3 endpoint benchmark, now with alert evaluation on
ingest).
